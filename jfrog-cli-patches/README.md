                                  └─ docker        ─> docker-build-push.yaml                 (changed)

What each published artifact gets:

| | Maven / Gradle release & snapshot | Docker image |
|---|---|---|
| Published with | `jf mvn deploy` / `jf gradle artifactoryPublish` | `docker/build-push-action` + `jf rt build-docker-create` |
| Authentication | GitHub OIDC → short-lived JFrog token | same |
| JFrog build-info | `<repo>` / `<repo>-snapshot` | `<repo>-docker` |
| SBOM | CycloneDX, deployed next to the artifacts | SPDX, generated by BuildKit, stored in the image index |
| Provenance | GitHub SLSA attestation of the distribution zip | BuildKit SLSA provenance in the image + GitHub SLSA attestation |
| SBOM attestation | GitHub attestation of the distribution zip | (the BuildKit SBOM is itself an in-toto attestation in the image) |
| Where attestations live | GitHub + JFrog evidence on the zip | GitHub + OCI referrer in the registry + JFrog evidence on the image |

## 2. Shared workflows (e-CODEX/workflows)

### Common building blocks (and why)

- **`jfrog/setup-jfrog-cli` v5.3.5, JFrog CLI pinned to 2.133.0.** Installs the CLI and logs in with the GitHub OIDC
  token, using the OIDC integration `setup-jfrog` on scm.ecodex.eu. No long-lived credentials are stored in GitHub. The
  CLI version is pinned so builds are reproducible and a new CLI release cannot break a release run.
  Its **post step** runs at the end of the job. It:
  - adds the git details to the build-info and publishes it, if it was not published yet;
  - turns every GitHub attestation created in the job into JFrog evidence (`jf evd create --sigstore-bundle`).
- **`JFROG_CLI_BUILD_NAME`.** The default build-info name is the caller's workflow name ("Manual Release Workflow").
  That name is the same in every repository, and the Maven/Gradle job and the Docker job of one run would overwrite each
  other. Each workflow therefore sets an explicit name: `<repo>`, `<repo>-snapshot` or `<repo>-docker`.
- **GitHub attestations (`actions/attest`, `actions/attest-build-provenance`).** These are signed with Sigstore using the
  job's OIDC identity and stored in GitHub. Anyone can verify them with
  `gh attestation verify <file or oci://image@digest> --repo <owner>/<repo>`. They prove which repository, workflow,
  commit and runner produced the artifact.
- **Permissions.**
  - `id-token: write`: the JFrog login and attestation signing.
  - `attestations: write`: storing attestations in GitHub.
  - `contents: write`: dependency submission, where used.
- **Every action pinned by commit SHA**, with the version in a comment. This prevents supply-chain attacks through moved tags.

### `maven-publish-release.yaml` / `maven-publish-snapshot.yaml`

| Step | What | Why |
|---|---|---|
| Checkout | the release tag (release) or the pushed commit (snapshot) | build exactly what was tagged |
| Check if version is Snapshot | snapshot workflow only | a develop push must never overwrite a release version |
| Setup JFrog CLI | OIDC login | see above |
| Dependency submission | dependency graph to GitHub | Dependabot / Advanced Security alerts |
| `jf mvn-config` + `jf mvn deploy` | deploys all modules to `deploy-repo` with the JFrog Maven extractor | records artifacts and resolved dependencies in the build-info; no credentials in settings.xml. The CycloneDX plugin (bound to `package` in the POM) attaches the SBOMs, so they are deployed too |
| Locate the distribution | finds the deployed zip in Artifactory by sha256 | Maven renames the zip when it deploys it (and snapshots get timestamps), and the attestation subject must be its real Artifactory path |
| Attest provenance | SLSA provenance of the zip | proves how and where the zip was built |
| Attest SBOM | `target/bom.json` bound to the zip | signed link between the zip and its SBOM |
| (post) setup-jfrog-cli | publishes the build-info and creates the JFrog evidence on the zip | provenance visible and enforceable in Artifactory |

Inputs: `java-version`, `maven-parameters`, `deploy-repo` (default `ecodex-releases` / `ecodex-snapshots`),
`distribution-path` (**required**), `sbom-path` (default `target/bom.json`), `tag`, `environment`.
`maven-repo-id` is kept so existing callers don't break, but it is ignored.

### `gradle-publish-release.yaml` / `gradle-publish-snapshot.yaml`

The steps are the same as for Maven, with these differences:
- `jf gradle-config --use-wrapper --deploy-ivy-desc=false`, then
  `jf gradle clean cyclonedxBom artifactoryPublish --no-configuration-cache`:
  - all Gradle publications are deployed, including the `connector-distribution` zip;
  - Ivy descriptors are not wanted in a Maven repository;
  - the JFrog extractor is injected by an init script, which does not support the configuration cache.
- The aggregated CycloneDX SBOM (`build/reports/cyclonedx/bom.json`) is not a Gradle publication. It is uploaded next
  to the zip as `<zip>-cyclonedx.json` with `jf rt upload`, which also adds it to the build-info.

Inputs: `java-version`, `gradle-parameters`, `deploy-repo` (default `libs-release` / `libs-snapshot`),
`distribution-path` (**required**), `sbom-path`, `tag`, `environment`. `maven-repo-id` is deprecated.

### `docker-build-push.yaml`

| Step | What | Why |
|---|---|---|
| Checkout | the tag (release / refresh) or the pushed commit | build exactly the released source |
| Setup Buildx | BuildKit builder | needed for SBOM and provenance attestations |
| Setup JFrog CLI + Docker login | OIDC token used as the registry password | no stored registry credentials |
| Metadata | tags: `1.2.3`, `1.2`, `1`, `latest`, `sha-*`, `edge` (see refresh below); OCI labels | SemVer / GitFlow tagging |
| Build and push | `pull: true`, `no-cache` on refresh, `sbom: true`, `provenance: mode=max` | newest base image; SBOM and full provenance stored with the image |
| `jf rt build-docker-create` | adds the pushed image (tags + digest) to the build-info `<repo>-docker` | traceability in Artifactory; Xray can scan the build |
| Attest (registry) | `push-to-registry: true`, plain image name | the attestation sits in the registry as an OCI referrer; registry-only tools (cosign, oras, `gh attestation verify --bundle-from-oci`) can verify it |
| Attest (JFrog) | subject `oci://<registry>/<image>` | the setup-jfrog-cli post step recognises it and attaches it to the image as JFrog evidence |
| (post) setup-jfrog-cli | publishes the build-info and creates the evidence | |

**Why two attestation steps:** `actions/attest` can only push an attestation to a registry when the subject is a plain
image name. JFrog only recognises an image subject written as `oci://...`. So one attestation cannot serve both. The
post step tries to create evidence from *every* attestation of the job, so it logs **one expected warning** for the
registry attestation, whose plain name is not an Artifactory path. The evidence from the `oci://` attestation is still
created.

Inputs: `image-name`, `tag`, `environment`, `registry` (`<host>/<docker-repo>`, default `scm.ecodex.eu/docker`),
`refresh`, `floating-tags`, `latest`.

#### Refresh mode (`refresh: true`): fix image vulnerabilities without a new release

- **Same source:** the released git tag is checked out, so the application is built from exactly the released code.
- **Fresh OS layers:** `pull: true` and `no-cache: true` mean the newest base image is used and every layer is rebuilt,
  including `apt-get upgrade`.
- **Tag overwrite:** only the `1.2.3` tag is overwritten by default.
  - `1.2` and `1` move only with `floating-tags`; use it when refreshing the newest patch of that line.
  - `latest` moves only with `latest`; use it when refreshing the newest release.
  - `edge` and `sha-*` never move.

  This way, refreshing an old release can never take those tags away from a newer one.
- **New build-info:** the refreshed image gets its own build-info, attestations and evidence, like a release.

## 3. connector and connector-ng (callers)

- **`publish-release.yaml`** (manual): check-version → tag-version → publish (Maven/Gradle) + docker. Changes:
  - **Explicit permissions:** `permissions: {}` at the top and the minimum per job. This is required: a reusable
    workflow can only use `id-token: write` if the caller grants it.
  - **New shared workflows:** the jobs call the JFrog CLI shared workflows (`@main`; pin a SHA after merging upstream)
    with `deploy-repo` and `distribution-path`:
    - connector-ng: `connector-distribution/build/connector-distribution-*.zip`;
    - connector: `domibusConnectorDistribution/target/domibusConnector.zip`.
- **`publish-snapshot.yaml`** (push to develop): publish + docker to `scm.ecodex.eu/ecodex-docker-snapshots`, with
  the same permission changes.
- **`docker-refresh.yaml`** (new, manual):
  - Inputs: `tag` (required), `floating-tags`, `latest`, `environment`. It calls `docker-build-push.yaml` with `refresh: true`.
  - A `concurrency` group per tag prevents two refreshes of the same tag racing each other.
- **connector-ng `Dockerfile`:** `apt-get update && apt-get upgrade -y` in the runtime stage, as connector already
  does. Without it, a refresh would only get fixes that are already in the base image. A refresh uses the Dockerfile of
  the old tag, so this only helps tags released after this change.

### Using the refresh

Actions → **Refresh Docker Image** → Run workflow → `tag` = e.g. `7.1.0`. Tick *floating-tags* / *latest* only for the
newest patch / release.

## 4. How to apply (Codespaces)

```bash
# 0. get the patches
git fetch https://github.com/zugazagoitia/connector-ng claude/jfrog-cli-workflows-bdvr86
git checkout FETCH_HEAD -- jfrog-cli-patches && unzip -o jfrog-cli-patches/jfrog-cli-patches.zip -d /tmp/jfrog-patches
git rm -rq --cached jfrog-cli-patches && rm -rf jfrog-cli-patches   # don't keep them in your branch
# (or download the zip from the branch on GitHub)

# 1. sync the fork with upstream (or use GitHub's "Sync fork" button)
#   workflows:    git fetch upstream && git checkout -b feat/jfrog-cli-releases upstream/main   (then skip step 2's checkout)
#   connector-ng: git fetch upstream && git checkout develop && git merge --ff-only upstream/develop
#   connector:    already up to date
#   (git remote add upstream https://github.com/e-CODEX/<repo>.git if needed)

# 2. apply
git checkout -b feat/jfrog-cli-releases
git am /tmp/jfrog-patches/<repo>-jfrog-cli.patch
```

The connector-ng branch `claude/jfrog-cli-workflows-bdvr86` already contains the connector-ng change, so in that fork
you can use the branch directly instead of the patch.

### Testing from your forks

The callers reference `e-CODEX/workflows/...@main`, so the patches are ready to go upstream as-is. To run them from your
forks, run this in all three repos (the shared workflows also reference `install-graphviz` by repo path):

```bash
grep -rl 'e-CODEX/workflows/' .github | xargs sed -i 's#e-CODEX/workflows/#zugazagoitia/workflows/#g'
```

## 5. JFrog prerequisites

- **OIDC integration:** `setup-jfrog`, with an identity mapping for each repository. This is already used today.
- **Permissions for the mapped identity:**
  - Deploy on `libs-release` / `libs-snapshot` (connector-ng), `ecodex-releases` / `ecodex-snapshots` (connector) and
    the Docker repositories;
  - **Delete/Overwrite on the Docker repositories**, because a refresh overwrites a tag;
  - publish build-info, and Annotate (evidence).
- **Evidence service:** JFrog evidence needs the Evidence service (Enterprise+). Without it, `setup-jfrog-cli` only logs a
  warning at the end of the job. GitHub attestations are created either way.

## 6. Not run end-to-end

These patches have not been run against scm.ecodex.eu. Check these on the first runs:
- `jf gradle` with Gradle 9.8 (`--no-configuration-cache`). The snapshot workflow on `develop` will show it first.
- The distribution lookup by sha256 for connector's Maven `pom`-packaged distribution module. The zip is deployed today
  as `domibusConnectorDistribution-<version>.zip`.
- Overwriting a Docker tag needs the permission listed above.
- The expected evidence warning for the registry attestation (section 2).
