= Business Domain Configuration

At startup, `ConnectorBusinessDomainInitializer` registers the business domains declared
under `connector.business-domains.defaults`, together with the processing mode (PMode)
attached to each of them.

The initializer is idempotent: domains and processing modes that are already registered
are skipped silently, so restarting the connector is safe. Any other failure — an
unreadable file, a malformed PMode definition, a truststore that cannot be opened —
aborts startup rather than leaving the connector half-configured.

If no default is configured and no business domain exists yet, the connector registers a
single built-in default domain so that it can start in a usable state.

== Properties
Configuration is provided via `application.properties` under the `+connector.business-domains.*+` prefix.

.Business Domains Configuration
[cols="35,40,10,15", options="header"]
|===
| Property | Description | Optional | Example

| `connector.business-domains.defaults[n].identifier`
| Message lane identifier of the business domain. Must be unique across the connector. *Keep `default_business_domain`* for the domain that carries the gateway and SOAP backend traffic (see the warning below).
| No
| `default_business_domain`

| `connector.business-domains.defaults[n].description`
| Free-text description, shown in the administration UI. Must not be empty.
| No
| `Default business domain`

| `connector.business-domains.defaults[n].enabled`
| Whether the domain accepts messages. Defaults to `false`.
| Yes
| `true`

| `connector.business-domains.defaults[n].pmode.file`
| Processing mode definition (XML, as exported from the gateway) registered for the domain. When absent, no processing
mode is registered and the remaining `+pmode.*+` properties are ignored. If the file cannot be read, startup is aborted.
| Yes
| `file:./config/pmode/<your-pmode>.xml`

| `connector.business-domains.defaults[n].pmode.truststore`
| Truststore holding the certificates of the parties declared in the processing mode. It is also the truststore used to validate the signature of the ASiC-S containers and tokens of inbound messages, so it must contain the signing certificates of the partner connectors. The store type is derived from the file extension (`.jks`, `.keystore` = JKS; `.p12`, `.pfx` = PKCS12).
Required as soon as `pmode.file` is set.
| Yes
| `file:./config/pmode/<pmode-truststore>.jks`

| `connector.business-domains.defaults[n].pmode.truststore-password`
| Password protecting the truststore. Required as soon as `pmode.file` is set.
| Yes
| `${PMODE_TRUSTSTORE_PASSWORD}`

|===

[WARNING]
====
In this version, messages received from the gateway, messages submitted through the SOAP backend API, inbound evidences and the routing rules are always assigned to the business domain `default_business_domain`.
Keep this identifier for your main domain and attach your P-Mode to it. Additional business domains can only be used by backends submitting through the REST API with an explicit business domain identifier.
====

[NOTE]
====
A processing mode is bound to exactly one business domain, and a business domain can hold
at most one processing mode. Declaring a second processing mode for the same domain is
rejected.
====

== Location syntax

`pmode.file` and `pmode.truststore` are resolved as Spring resource locations. The prefix
determines where the resource is read from:

[cols="1,3", options="header"]
|===
| Prefix | Resolved from

| `file:`
| The filesystem, relative to the working directory or as an absolute path.

| `classpath:`
| The application classpath — useful for bundling a default configuration.

| `http:`, `https:`
| A remote endpoint, read once at startup.
|===

[WARNING]
====
A location without a prefix is resolved from the *classpath*, not the filesystem.
Filesystem paths must be written as `file:./config/pmode/<your-pmode>.xml`. Deployments
migrating from connector 6.x, where bare paths were treated as filesystem paths, must
add the prefix.
====

.Configuration Example
[source,properties]
----
connector.business-domains.defaults[0].identifier=default_business_domain
connector.business-domains.defaults[0].description=<description>
connector.business-domains.defaults[0].enabled=true
connector.business-domains.defaults[0].pmode.file=file:./config/pmode/<your-pmode>.xml
connector.business-domains.defaults[0].pmode.truststore=file:./config/pmode/<pmode-truststore>.jks
connector.business-domains.defaults[0].pmode.truststore-password=${PMODE_TRUSTSTORE_PASSWORD}
----

TIP: Additional domains can be declared by incrementing the index: `connector.business-domains.defaults[1]`, `connector.business-domains.defaults[2]`, etc.

== Registering a processing mode after startup

Configuring `pmode.file` is optional. A business domain declared without one starts
without a processing mode and cannot exchange messages until one is registered.

The processing mode and its truststore can then be uploaded at any time through the
administration API, or through the *Processing modes* screen of the administration UI,
which posts to the same endpoint.

=== Via the administration UI

Navigate to *Processing modes* in the administration UI and use the upload form to
submit the processing mode file and its truststore.

image::load_pmode.png[Processing modes upload screen,align="center"]

=== Via the administration API

IMPORTANT: All administration API endpoints require a valid JWT bearer token, and registering a processing mode requires the `ADMIN` role.
Obtain a token by authenticating against the login endpoint first (see <<user-authentication>>), then
include it in every subsequent request via the `Authorization` header.

[source,http]
----
POST /api/v1/admin/processing-modes
Content-Type: multipart/form-data
Authorization: Bearer <token>
----

.Request parts
[cols="3,4,1,3", options="header"]
|===
| Part | Description | Optional | Example

| `businessDomainIdentifier`
| Identifier of the business domain the processing mode is registered against. The domain
must already exist.
| No
| `default_business_domain`

| `description`
| Free-text description of the processing mode.
| No
| `<P-Mode of the ... use case>`

| `processingModeFile`
| Processing mode definition. Must be an XML document.
| No
| `<your-pmode>.xml`

| `truststore.truststoreFile`
| Truststore holding the certificates.
Must be a `.jks`, `.keystore`, `.p12` or `.pfx` file.
| No
| `<pmode-truststore>.jks`

| `truststore.password`
| Password protecting the truststore.
| No
| `<truststore-password>`
|===

.Step 1 — Obtain a bearer token
[source,bash]
----
TOKEN=$(curl -s -X POST https://<connector-host>/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<admin-user>","password":"<password>"}' \
  | jq -r '.accessToken')
----

NOTE: The login response also contains `refreshToken`, `expiresIn`, `refreshExpiresIn` and `mustChangePassword`.
When `mustChangePassword` is `true` (first login with the configured admin password), change the password with `POST /api/v1/auth/change-password` before using the administration API.
`<connector-host>` is the address of your reverse proxy (or `localhost:<server.port>` on the Connector host).

.Step 2 — Register the processing mode
[source,bash]
----
curl -X POST https://<connector-host>/api/v1/admin/processing-modes \
  -H "Authorization: Bearer ${TOKEN}" \
  -F "businessDomainIdentifier=default_business_domain" \
  -F "description=<P-Mode of the ... use case>" \
  -F "processingModeFile=@./config/pmode/<your-pmode>.xml;type=application/xml" \
  -F "truststore.truststoreFile=@./config/pmode/<pmode-truststore>.jks" \
  -F "truststore.password=<truststore-password>"
----
