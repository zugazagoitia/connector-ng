= Routing Rule Configuration

This configuration defines the routing behavior used by the connector to determine to which backend system a message should be transported.

Routing rules allow dynamic selection of backend destinations based on the AS4 properties of the inbound message.

The backend of an inbound message is resolved in this order:

. If the message belongs to a conversation (AS4 `ConversationId`) already associated with a backend, it is delivered to that backend (e.g. replies and evidences).
. Otherwise, if routing is enabled, the rules are evaluated in index order and the first matching rule determines the backend. The built-in rule for connector-to-connector test messages is evaluated after your rules.
. Otherwise, the message is delivered to `default-backend-name`.

The `link-name` and `default-backend-name` values must name a declared link partner.

NOTE: Routing rules apply to the default business domain only.

IMPORTANT: The template routes the test service `Test` to the test partner `backend_alice`. Replace the rules and the default backend with your own services and link partner names.

== Basic configuration
Configuration is provided via `application.properties` under the `+connector.routing.*+` prefix.

.Backend Routing Configuration Properties
[cols="35,40,10,15", options="header"]
|===
| Property | Description | Optional | Example

| `connector.routing.enabled`
| Master switch for message routing logic. When `false`, the rules below are ignored and inbound messages are routed to `default-backend-name`. When `true`, a built-in rule is added that sends connector-to-connector test messages to the internal test backend: it matches the service name and type of `+connector.c2ctests.service.*+` *or* the action `connector.c2ctests.action` (by default `Connector-TEST`, `urn:e-codex:services:`, `ConTest_Form`).
| Yes
| By default, `false` (in connector 6.x the default was `true`)

| `connector.routing.default-backend-name`
| Name of the link partner that receives inbound messages when routing is disabled or no rule matches. Required when `connector.routing.enabled` is `true` (the startup validation fails otherwise). If routing is disabled and the property is omitted, the Connector uses `default_backend`, which only works if a link partner has that name.
| Yes (No if routing is enabled)
| `<backend-courts>`

| `connector.routing.backend-rules[*index*].link-name`
| Name of the target link partner (must match `connector.link.backend[n].link-partners[m].name`). Use one rule per link partner. To combine several conditions for the same partner, nest them in one `match-clause` with `\|(...)` or `&(...)`.
| No
| `<backend-registry>`

| `connector.routing.backend-rules[*index*].description`
| Free-text description of the rule.
| Yes
| `<Land registry messages>`

| `connector.routing.backend-rules[*index*].match-clause`
| Expression evaluated against the AS4 properties of the inbound message (see the grammar below). Rules are evaluated in index order; the first matching rule wins.
| No
| `equals(ServiceName, '<service>')`

|===

NOTE: The configuration is validated at startup. If routing is enabled, a missing
`default-backend-name`, or a rule without `link-name` or `match-clause`, stops the connector
with an error naming the offending property.
A match clause that cannot be parsed makes the backend resolution of *every* inbound message fail (`Could not parse routing rule pattern: ...`) as long as the message is not assigned by its conversation, also when routing is disabled. Check your clauses against the grammar below, and send one inbound test message after each change.

.Configuration Example
[source,properties]
----
connector.routing.enabled=true
# backend receiving everything that no rule matches
connector.routing.default-backend-name=<backend-courts>
# messages of one service go to another backend
connector.routing.backend-rules[0].link-name=<backend-registry>
connector.routing.backend-rules[0].description=<Land registry messages>
connector.routing.backend-rules[0].match-clause=equals(ServiceName, '<registry-service>')
# several conditions for the same backend are combined in ONE rule ('|' = or, '&' = and)
connector.routing.backend-rules[1].link-name=<backend-insolvency>
connector.routing.backend-rules[1].match-clause=|(equals(ServiceName, '<service-a>'),startswith(Action, '<prefix>'))
# several conditions can also be nested: Action starts with a prefix and the service is not a given one
connector.routing.backend-rules[2].link-name=<backend-orders>
connector.routing.backend-rules[2].match-clause=&(startswith(Action, '<prefix>'),not(equals(ServiceName, '<service-b>')))
----

TIP: Service names, service types and actions are those of your P-Mode. `FromPartyId`, `FromPartyRole` and `FinalRecipient` can also be used (see the restrictions below the grammar).

[[routing-pattern]]
.Match clause grammar
[source]
----
<ROUTING_RULE_PATTERN> ::= <BOOLEAN_EXPRESSION> | <COMPARE_EXPRESSION> | <NOT_EXPRESSION>
<BOOLEAN_EXPRESSION> ::= <OPERAND>(<ROUTING_RULE_PATTERN>, <ROUTING_RULE_PATTERN>)
<COMPARE_EXPRESSION> ::= equals(<AS4_TYPE>, '<VALUE>') | startswith(<AS4_TYPE>, '<VALUE>')
<NOT_EXPRESSION> ::= not(<ROUTING_RULE_PATTERN>)
<OPERAND> ::= "&" | "|"
<AS4_TYPE> ::= ServiceType | ServiceName | FinalRecipient | Action | FromPartyId | FromPartyRole
<VALUE> ::= one or more of: letters, digits, _ : @ - ~ . / # ?
----

* The value must be written between single quotes and must not be empty. Only the characters listed for `<VALUE>` are allowed; spaces, `+`, `=`, `'`, `\`, `|`, `&`, `(` and `)` are not. Values such as `urn:e-codex:services:` are accepted.
* Function and attribute names are case-sensitive and must be written exactly as shown (`equals`, `startswith`, `not`, `ServiceName`, ...). Comparisons of values are case-sensitive as well.
* Spaces between the elements are allowed (`equals(ServiceName, 'EPO')` and `equals(ServiceName,'EPO')` are equivalent).
* `&` and `|` take exactly two operands. Nest them to combine more conditions, for example `+|(equals(Action, 'A'),|(equals(Action, 'B'),equals(Action, 'C')))+`. * Use `equals` rather than `startswith` for optional attributes such as `FinalRecipient`, which may be absent from a message.
* `ToPartyId`, `ConversationId` and other AS4 properties are not supported.
