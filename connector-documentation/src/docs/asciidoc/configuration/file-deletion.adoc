= Files cleanup

The connector deletes the files of attachments that are no longer needed, in three ways.
Two of them are scheduled jobs with their own age threshold and schedule; the third one runs as soon as a message is resolved.

[cols="2,3,2", options="header"]
|===
| Clean-up | What is deleted | Configuration

| Orphaned attachments (scheduled)
| Attachments not linked to any message: file in the storage *and* attachment row in the database.
| `connector.file-deletion.orphan.*`

| Unresolved messages (scheduled)
| Messages that were neither confirmed nor rejected: attachment files, then the message itself and its database rows.
| `connector.file-deletion.unresolved-messages.*`

| Resolved messages (immediate)
| Messages confirmed or rejected by an evidence: attachment files; the message is kept with status `DELETED`.
| No property (queue `connector.queues.resolved-message-cleanup-processing-queue`)
|===

== Common configuration

Configuration is provided via `application.properties` under the `connector.file-deletion.*`
prefix. Every job has the same two properties: `threshold` and `cron`.

=== Threshold format

The threshold accepts the standard Spring Boot duration formats:

[cols="1,2", options="header"]
|===
| Value | Meaning

| `30m` | 30 minutes
| `12h` | 12 hours
| `1d` | 1 day
| `PT36H` | 36 hours (ISO-8601)
|===

A value without a unit (for example `60`) is interpreted as milliseconds.

=== Cron format

The cron expression is a Spring cron expression with six fields, starting with the seconds:

----
 ┌───────── second        (0-59)
 │ ┌─────── minute        (0-59)
 │ │ ┌───── hour          (0-23)
 │ │ │ ┌─── day of month  (1-31)
 │ │ │ │ ┌─ month         (1-12)
 │ │ │ │ │ ┌ day of week  (0-7 or MON-SUN)
 │ │ │ │ │ │
 0 0 0 * * *
----

[cols="2,3", options="header"]
|===
| Expression | Runs

| `0 0 0 * * *` | every day at 00:00:00
| `0 10 0 * * *` | every day at 00:10:00
| `0 0 * * * *` | every hour
| `0 */15 * * * *` | every 15 minutes
|===

The jobs run in the default time zone of the JVM. In containers this is often UTC, so
"midnight" may not correspond to midnight in your local time zone.

NOTE: In a `.properties` file, do not wrap the cron expression in quotes: they would become part
of the value. In YAML, quotes are required because of the `*` characters.

=== Common behavior

* The file is deleted from the storage first. The database is updated only after the deletion succeeded (see each job for what is updated).
* If the deletion of one file fails, the error is logged, the other attachments are still
processed, and the failed attachment is retried at the next run.
* Attachments that already have a deletion date are never processed again.
* Deleting a file that no longer exists is not an error.

WARNING: Deleted files cannot be recovered.

== Orphaned attachments cleanup

An attachment is *orphaned* when it is not linked to any message (`MESSAGE_ID` is `null`).
This happens, for example, when a file was uploaded but the message it belonged to was never created.

A scheduled job periodically looks for orphaned attachments that are older than a configurable
threshold, deletes their content from the file storage (for example the S3 bucket), and then *deletes the attachment rows* from the database (verified: an uploaded file that was never used in a message disappears from `connector_message_attachments`).

[cols="3,4,1,3", options="header"]
|===
| Property | Description | Optional | Example

| `connector.file-deletion.orphan.threshold`
| Minimum age of an orphaned attachment before its file is deleted.
The age is computed from the attachment creation date (`CREATED_AT`, stored in UTC).
| Yes (default: `1d`)
| `connector.file-deletion.orphan.threshold=1d`

| `connector.file-deletion.orphan.cron`
| Schedule of the cleanup job.
Set to `-` to disable the job.
| Yes (default: `0 0 0 * * *`)
| `connector.file-deletion.orphan.cron=0 0 0 * * *`
|===

.Configuration Example
[source,properties]
----
# Delete the files of orphaned attachments that are at least 1 day old
connector.file-deletion.orphan.threshold=1d

# Run the cleanup every day at 00:00:00
connector.file-deletion.orphan.cron=0 0 0 * * *
----

NOTE: With a threshold of `1d` and a daily schedule, an orphaned attachment is deleted between
24 hours and almost 48 hours after its creation, depending on when it was created relative to the
next run.

== Unresolved messages cleanup

A message is *unresolved* when it was neither confirmed nor rejected
(both `CONFIRMED_AT` and `REJECTED_AT` are `null`) and is older than a configurable threshold.
Such a message is considered as never receiving an outcome.

A scheduled job periodically looks for unresolved messages that are older than the threshold,
deletes the content of their attachments from the file storage (for example the S3 bucket), and then
*permanently deletes the message* from the database: the message row and its attachments, evidences,
business document, AS4 properties and transport steps. The message is no longer visible in the
administration API.

WARNING: Inbound messages are also concerned. An inbound message is confirmed when a `DELIVERY` evidence is
created for it, either by the backend or automatically (`connector.message-processing.auto-trigger-delivery-evidences`).
If neither happens within the threshold, the message and its files are deleted.
Choose the threshold accordingly, and back up the database if you need a record of such messages.

[cols="3,4,1,3", options="header"]
|===
| Property | Description | Optional | Example

| `connector.file-deletion.unresolved-messages.threshold`
| Minimum age of an unresolved message before it and its attachment files are deleted.
The age is computed from the message creation date (`CREATED_AT`, stored in UTC).
| Yes (default: `7d`)
| `connector.file-deletion.unresolved-messages.threshold=7d`

| `connector.file-deletion.unresolved-messages.cron`
| Schedule of the cleanup job.
Set to `-` to disable the job.
| Yes (default: `0 10 0 * * *`)
| `connector.file-deletion.unresolved-messages.cron=0 10 0 * * *`
|===

.Configuration Example
[source,properties]
----
# Messages neither confirmed nor rejected
# Delete unresolved messages (and their files) that are at least 7 days old
connector.file-deletion.unresolved-messages.threshold=7d

# Run the cleanup every day at 00:10:00
connector.file-deletion.unresolved-messages.cron=0 10 0 * * *
----

NOTE: This job runs at 00:10:00, ten minutes after the orphaned attachments job (00:00:00), so
the two jobs do not start at the same moment.

NOTE: With a threshold of `7d` and a daily schedule, an unresolved message is deleted
between 7 and almost 8 days after its creation, depending on when it was created relative to the
next run.

=== Behavior

* Only messages with no confirmation date and no rejection date are processed.
* Only the attachments of these messages that are not yet marked as deleted are processed.
* If a file of a message cannot be deleted, the message is kept and retried at the next run; the other
messages are still processed. The job logs a summary: `Unresolved messages cleanup done: [n] messages deleted, [n] failed; files: [n] deleted, [n] failed`.

== Resolved messages cleanup

When an evidence resolves a message (positive: `DELIVERY`, `RETRIEVAL`; negative: `SUBMISSION_REJECTION`,
`NON_DELIVERY`, `NON_RETRIEVAL`, `RELAY_REMMD_REJECTION`, `RELAY_REMMD_FAILURE`), the Connector sets
`CONFIRMED_AT` or `REJECTED_AT` and publishes an event on the queue
`connector.queues.resolved-message-cleanup-processing-queue`. Its listener deletes the attachment files at
once, marks the attachments as deleted (`DELETED_AT`), and sets the message to the status `DELETED`. The message,
its evidences and its transport steps are kept in the database.

There is no property for this clean-up and no delay: after the confirmation, the business document and
attachments of the message can no longer be downloaded. If a file cannot be deleted, the event is redelivered
by the broker (see the connector queue chapter).

NOTE: Keep the default value of `connector.queues.resolved-message-cleanup-processing-queue`.
