= Migrate Configuration From 6.x to 7.x

== Overview

Connector 7.x is a new implementation. Its configuration file (now `application.properties` instead of `connector.properties`) keeps the structure of 6.x for most sections, with the following changes:

* *Infrastructure*: the embedded Artemis broker is replaced by an external Apache ActiveMQ Classic broker shared with the gateway; the gateway is reached through the Domibus JMS plugin instead of the connector web-service plugin; file storage moves to an S3-compatible object store; Java 21 is required.
* *Renamed sections*: message processing (`+processing.*+`), C2C tests (`+c2ctests.*+`), initial admin user and P-Mode upload (`+connector.init.*+`), DSS cache and proxy, REM evidences, container, business document validation, backend links.
* *New sections*: REST API authentication (JWT), CORS.
* *Removed sections*: gateway link (`connector.link.gateway`), embedded broker (`+spring.artemis.*+`), evidence timeouts, content deletion, filesystem/database storage, UI settings (see <<migration-removed>>).
* *Changed defaults and behaviour*: routing is disabled by default, the P-Mode verification defaults are swapped, at most one routing rule per backend (see <<migration-behaviour>>).
* *Property naming*: hyphenated store segments (`key-store`, `trust-store`) become `keystore`, `truststore`; filesystem locations must use the `file:` prefix.

IMPORTANT: As in 6.x, the shipped configuration file is a template with test values. Do not merge it blindly with your 6.x file: start from your 6.x values, map them with the tables below, and fill the new sections as described in the chapter on preparing `application.properties`.

WARNING: Connector 6.x failed at startup on invalid properties (`connector.common.fail-on-invalid-property=true`). Connector 7.x silently ignores unknown properties: a property that keeps its 6.x name does not cause an error at startup; it simply has no effect.
Review the startup log and the configuration exposed by the administration portal after migrating.

NOTE: This chapter covers the configuration file only. Migration of the 6.x database content is not covered.

== Step-by-step Migration

NOTE: Across all sections, hyphenated store property segments (`key-store`, `trust-store`)
have been normalised to their unhyphenated equivalents (`keystore`, `truststore`) in 7.x.

=== Business Domain Configuration

NOTE: In 6.x, business domains (message lanes) existed but were managed in the database, with the default lane `defaultBusinessDomain`, and the P-Mode could be uploaded at first start with `+connector.init.pmode.*+`.
In 7.x, the default domain is called `default_business_domain` and is declared, together with its P-Mode, under `+connector.business-domains.defaults[n].*+`.
Keep the identifier `default_business_domain`: gateway and SOAP backend traffic is always assigned to it in this version.

.Initial P-Mode upload
|===
| Old property (6.x) | New property (7.x) | Notes

| `connector.init.pmode.enabled`
| _(removed)_
| The P-Mode is registered when `pmode.file` is set.

| `connector.init.pmode.upload[n].p-mode-xml`
| `connector.business-domains.defaults[n].pmode.file`
| `file:` prefix required for filesystem paths.

| `connector.init.pmode.upload[n].trust-store.path`
| `connector.business-domains.defaults[n].pmode.truststore`
|

| `connector.init.pmode.upload[n].trust-store.password`
| `connector.business-domains.defaults[n].pmode.truststore-password`
|

| `connector.init.pmode.upload[n].trust-store.type`
| _(removed)_
| The type is derived from the file extension (`.jks`, `.keystore`, `.p12`, `.pfx`).

| `connector.init.pmode.upload[n].business-domain-name`
| `connector.business-domains.defaults[n].identifier`
| Use `default_business_domain`.
|===

IMPORTANT: If none of the properties below are set and no business domain exists yet, the connector
creates a default domain on startup. Set them explicitly if you need to control
the domain identifier, description, or P-Mode location.

.New Business Domain Configuration Properties (7.x)
|===
| Property | Default | Required | Notes

| `connector.business-domains.defaults[0].identifier`
| `default_business_domain`
| No
| Logical name of the default business domain

| `connector.business-domains.defaults[0].description`
| `default business domain`
| No
| Human-readable description of the domain

| `connector.business-domains.defaults[0].enabled`
| `false`
| No
| Set to `true` so that the domain accepts messages

| `connector.business-domains.defaults[0].pmode.file`
| _(none)_
| No
| Location of the P-Mode file for this domain. Filesystem paths need the `file:` prefix.

| `connector.business-domains.defaults[0].pmode.truststore`
| _(none)_
| Yes, if `pmode.file` is set
| Truststore with the gateway certificates declared in the P-Mode.

| `connector.business-domains.defaults[0].pmode.truststore-password`
| _(none)_
| Yes, if `pmode.file` is set
| Password of the P-Mode truststore.
|===

.Minimal configuration example (7.x)
[source,properties]
----
connector.business-domains.defaults[0].identifier=default_business_domain
connector.business-domains.defaults[0].description=<description>
connector.business-domains.defaults[0].enabled=true
connector.business-domains.defaults[0].pmode.file=file:./config/pmode/<your-pmode>.xml
connector.business-domains.defaults[0].pmode.truststore=file:./config/keystores/<pmode-truststore>.jks
connector.business-domains.defaults[0].pmode.truststore-password=<your value from 6.x>
----

TIP: Additional domains can be configured by incrementing the index:
`connector.business-domains.defaults[1]`, `connector.business-domains.defaults[2]`, etc.

=== Message Processing Configuration

In 6.x, these properties existed under the `+processing.*+` prefix. They moved to `+connector.message-processing.*+` in 7.x, and the verification defaults changed.

.Renamed Message Processing Properties
|===
| Old property (6.x) | New property (7.x) | Notes

| `processing.send-generated-evidences-to-backend`
| `connector.message-processing.send-generated-evidences-to-backend`
| Renamed (default `true` in both).

| `processing.ebms-id-generator-enabled`
| `connector.message-processing.ebms-id-generator-enabled`
| Renamed (default `true` in both).

| `processing.ebms-id-suffix`
| `connector.message-processing.ebms-id-suffix`
| Renamed. The default changed from `ecodex.eu` to `connector.ecodex.eu`.

| `processing.outgoing-p-mode-verification-mode`
| `connector.message-processing.outbound-message-verification-mode`
| Renamed. *Default changed from `RELAXED` to `STRICT`.*

| `processing.incoming-p-mode-verification-mode`
| `connector.message-processing.inbound-message-verification-mode`
| Renamed. *Default changed from `STRICT` to `RELAXED`.*
|===

WARNING: The meaning of the verification modes also changed. In 6.x, `STRICT` required every P-Mode attribute (service and service type, action, party id, party id type and role) and `RELAXED` completed missing attributes from the P-Mode.
In 7.x, `STRICT` only checks the service and action, while `RELAXED` additionally checks the parties (see the message processing chapter).
Re-test your message exchange with the chosen modes.

.New Message Processing Properties (7.x)
|===
| Property | Default | Required | Notes

| `connector.message-processing.send-generated-evidences-to-backend`
| `true`
| No
| Whether REM evidences (submission acceptance/rejection, delivery/non-delivery)
are forwarded to the backend in addition to the gateway side

| `connector.message-processing.ebms-id-generator-enabled`
| `true`
| No
| When `true`, the connector generates ebMS message IDs itself rather than
relying on IDs supplied by the backend or gateway

| `connector.message-processing.auto-trigger-delivery-evidences`
| `false`
| No
| When `true`, a `DELIVERY` evidence is generated automatically once the message has been delivered to the backend

| `connector.message-processing.ebms-id-suffix`
| `connector.ecodex.eu`
| No
| Domain suffix appended to generated ebMS message IDs
(format: `<uuid>@<suffix>`). Only effective when the generator is enabled.

| `connector.message-processing.identifier-suffix`
| `connector.ecodex.eu`
| No
| Domain suffix used when generating connector message identifiers

| `connector.message-processing.transport-id-suffix`
| `connector.ecodex.eu`
| No
| Domain suffix used for transport step identifiers,
following the same `<value>@<suffix>` convention

| `connector.message-processing.outbound-message-verification-mode`
| `STRICT`
| No
| P-Mode verification of outbound messages (connector → gateway). See the message processing chapter.

| `connector.message-processing.inbound-message-verification-mode`
| `RELAXED`
| No
| P-Mode verification of inbound messages (gateway → connector). See the message processing chapter.
|===

NOTE: The three suffix properties (`ebms-id-suffix`, `identifier-suffix`,
`transport-id-suffix`) all follow the same `<value>@<suffix>` convention and
default to `connector.ecodex.eu` in the reference configuration. Set them to
a domain you control if you need generated IDs to be traceable to your deployment.

TIP: If migrating from 6.x where ebMS IDs were supplied externally, set
`ebms-id-generator-enabled=false` to preserve the previous behaviour until
you have confirmed your backend and gateway are compatible with connector-generated IDs.

.Configuration example (7.x)
[source,properties]
----
connector.message-processing.send-generated-evidences-to-backend=true
connector.message-processing.ebms-id-generator-enabled=true
connector.message-processing.ebms-id-suffix=connector.<your-organisation>.example
connector.message-processing.identifier-suffix=connector.<your-organisation>.example
connector.message-processing.transport-id-suffix=connector.<your-organisation>.example
connector.message-processing.outbound-message-verification-mode=STRICT
connector.message-processing.inbound-message-verification-mode=RELAXED
----

=== File Storage Configuration

All properties in this section are *new in 7.x*. 6.x did not use object storage.
In 7.x, S3-compatible object storage is the only supported storage backend,
and all five properties below are required.

.New File Storage Properties (7.x)
|===
| Property | Default | Required | Notes

| `connector.file.storage.s3.access-key`
| _(none)_
| Yes
| S3 access key ID.

| `connector.file.storage.s3.secret-key`
| _(none)_
| Yes
| S3 secret access key.

| `connector.file.storage.s3.region`
| _(none)_
| Yes
| AWS region (e.g. `eu-west-1`). For non-AWS providers this may be an
arbitrary placeholder value required by the S3 client.

| `connector.file.storage.s3.bucket`
| _(none)_
| Yes
| Name of the S3 bucket used to store connector files.

| `connector.file.storage.s3.endpoint`
| _(none)_
| Yes
| S3 endpoint URL. Required for non-AWS providers (MinIO, OVH Object Storage, etc.)
or when targeting a specific regional/VPC endpoint.

|===

.Configuration example (7.x)
[source,properties]
----
connector.file.storage.s3.access-key=${S3_ACCESS_KEY}
connector.file.storage.s3.secret-key=${S3_SECRET_KEY}
connector.file.storage.s3.region=us-east-1
connector.file.storage.s3.bucket=attachments
connector.file.storage.s3.endpoint=http://localhost:9000
----

# Timestamp servers (optional)

=== Message Routing

The property names of the backend routing rules are unchanged, but three behaviours changed:

[cols="1,2,2", options="header"]
|===
| Item | 6.x | 7.x

| `connector.routing.enabled`
| Default `true`: rules applied without setting the property.
| Default `false`. *Add `connector.routing.enabled=true`*, otherwise all inbound messages go to the default backend.

| Several rules for the same backend
| Allowed (rules ordered by `priority`).
| Only the last rule per `link-name` is kept; rules are evaluated in index order. Merge the conditions of a backend into one `match-clause` with `\|(...)`.

| Gateway routing (`+connector.routing.gateway-rules*+`, `default-gateway-name`)
| Available.
| Removed: a single gateway is used through the JMS broker.
|===

Rules apply to the default business domain only.

.Configuration Example (7.x)
[source,properties]
----
connector.routing.enabled=true
connector.routing.default-backend-name=<backend-name>
connector.routing.backend-rules[0].link-name=<other-backend-name>
connector.routing.backend-rules[0].match-clause=equals(ServiceName, '<service>')
----

=== Queues and Transactions

* The internal queues were renamed (6.x: `+connector.queues.to-connector-controller-queue+`, `to-link-queue`, `cleanup-queue` and their dead letter queues). Remove the 6.x queue properties and add all `+connector.queues.*+` properties of the 7.x template with their template values.
* JTA still uses Atomikos (`+spring.jta.*+`); the 6.x settings can be kept. The JTA log location (`spring.jta.log-file`) must be on persistent storage.
* Datasource: 6.x documented `spring.datasource.xa.data-source-class-name` for the XA class (or a JNDI datasource when deployed in Tomcat). Deployment in an external Tomcat and JNDI datasources are no longer supported.

=== 6.x properties without 7.x equivalent

The following 6.x settings have no equivalent in 7.x. Remove them, and check whether your operations relied on the corresponding feature.

[cols="2,3", options="header"]
|===
| 6.x properties | Situation in 7.x

| `+connector.controller.evidence.*+` (`timeoutActive`, `checkTimeout`, `relayREMMDTimeout`, `deliveryTimeout`, `retrievalTimeout` and the corresponding `+*WarnTimeout+` properties)
| *Feature not available.* 7.x does not generate `RELAY_REMMD_REJECTION` / `NON_DELIVERY` / `NON_RETRIEVAL` evidences when the expected evidence is not received in time. Monitor pending messages operationally.

| `+connector.controller.content.*+` (`check-timeout-enabled`, `check-timeout`)
| *Feature not available.* Message content is not deleted automatically; apply a lifecycle/retention policy on the S3 bucket and plan database housekeeping.

| `+connector.persistence.*+` (`default-large-file-provider-class`, `filesystem.storage-path`, `filesystem.create-dir`, `filesystem.encryption-active`)
| Replaced by S3 storage (`+connector.file.storage.s3.*+`). The Connector no longer encrypts stored content itself: enable server-side encryption on the bucket.

| `+connector.link.gateway.*+` (including `pull-interval`, `gw-address`)
| Replaced by the JMS queues of the Domibus default JMS plugin.

| `connector.link.backend[n].link-config.link-impl`, `link-partners[m].rcv-link-mode`
| Removed: one SOAP backend implementation; backends always submit by calling the Connector.

| `ocsp-enabled`, `crl-enabled`, `aia-enabled` of the certificate verifiers (e.g. `connector.business-document-sent.signature-validation.ocsp-enabled`)
| Always enabled; no longer configurable.

| `connector.business-document-sent.allow-system-type-override-by-client`
| Replaced by `connector.business-document.allowed-advanced-system-types`.

| `connector.instance-name`, `+connector.stage.*+`, `connector.common.fail-on-invalid-property`
| Removed.

| `+connector.ui.*+`, `server.servlet.session.cookie.name`
| Removed: the administration portal is a separate application using the stateless REST API.

| `spring.datasource.jndi-name`, `+spring.liquibase.*+`
| Removed: standalone deployment only; the database is initialised with the provided scripts.
|===

[[migration-behaviour]]
=== Behaviour changes to check

* *Routing* is disabled unless `connector.routing.enabled=true` is set, and only one rule per backend is kept (see above).
* *P-Mode verification*: defaults swapped and meaning changed (see the message processing section above).
* *Evidence issuer and container truststore*: in 6.x, the AS4 party of the evidence issuer and the container validation truststore were taken from the P-Mode upload. In 7.x, the issuer must be configured in `+connector.evidences.issuer.as4-party.*+`; the container truststore is still the P-Mode truststore.
* *Backend identification*: as in 6.x, the backend is identified by the DN of its signing certificate, but the configured `certificate-dn` must now be written entirely in lower case (see the link partner chapter).
* *Admin password*: no random password is generated anymore; the configured one is used.
