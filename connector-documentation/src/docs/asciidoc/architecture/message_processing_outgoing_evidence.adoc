[[message-processing-outgoing-evidence]]
= Processing of an outgoing evidence message

This chapter describes how evidence is generated and submitted when triggered from the backend or as a side effect of outbound business message processing.

== Evidence trigger from the backend

The backend can request evidence generation with an evidence trigger, either through the REST API (`POST /api/v1/messages/evidence-trigger`, handled by `ConnectorMessageController`) or through the SOAP API (`submitMessage` without message content and with one empty confirmation, handled by `ConnectorBackendWebServiceController`).
The trigger specifies the evidence type (for example `DELIVERY`) and references the business message that the backend received.

----

restTrigger --> ConnectorMessageController : POST
ConnectorBackendWebServiceController --> ConnectorOutboundEvidenceMessageReceiverService

ConnectorOutboundEvidenceMessageReceiverService --> ConnectorJmsOutboundEvidenceTriggerPublisher : verified trigger
ConnectorJmsOutboundEvidenceTriggerPublisher --> outboundEvidenceTriggerQueue

@enduml
----

`ConnectorOutboundEvidenceMessageReceiverService` assigns an identifier to the trigger and checks it before queuing it: a business message must match the reference (otherwise the REST API returns `404`), and that message must have been received from the gateway (direction `GATEWAY_TO_BACKEND`, otherwise `409`). The reference is looked up as an ebMS identifier, then as a backend message identifier, then as a Connector identifier. The trigger is then published to the outbound evidence trigger queue (`connector.queues.outbound-evidence-trigger-queue`) for asynchronous processing, and the caller receives the identifier of the trigger.

== Evidence trigger processing

`ConnectorJmsOutboundEvidenceTriggerListener` consumes trigger messages from the outbound evidence trigger queue and delegates to `ConnectorOutboundEvidenceMessageProcessorService` (the counterpart of `EvidenceMessageProcessor` and `EvidenceTriggerStep` in connector 6.x).

----
@startuml

outboundEvidenceTriggerQueue --> ConnectorJmsOutboundEvidenceTriggerListener
ConnectorJmsOutboundEvidenceTriggerListener --> ConnectorOutboundEvidenceMessageProcessorService
ConnectorOutboundEvidenceMessageProcessorService --> ConnectorMessageEvidenceCreator : 1. build REM evidence XML
ConnectorOutboundEvidenceMessageProcessorService --> ConnectorMessageEvidenceVerifier : 2. apply to business message
ConnectorOutboundEvidenceMessageProcessorService --> ConnectorEvidenceMessageCreator : 3. wrap as confirmation message
ConnectorOutboundEvidenceMessageProcessorService --> ConnectorLinkSubmitter : 4. to gateway\n5. to backend (optional)

@enduml
----

Processing steps:

. Resolve the referenced business message again and check that it was received from the gateway (`GATEWAY_TO_BACKEND`).
. Build the signed ETSI-REM evidence XML of the requested type using `ConnectorMessageEvidenceCreator` and `ConnectorEvidenceToolkitImpl`. The toolkit builds on the evidences that the message already has: an evidence whose predecessor in the REM chain is missing cannot be created, and the trigger fails.
. Apply the evidence to the business message with `ConnectorMessageEvidenceVerifier`: an evidence with a lower priority than one already received is ignored for the status; a positive evidence (`DELIVERY`, `RETRIEVAL`) sets the message to `CONFIRMED`, a negative one sets it to `REJECTED`.
. Create a confirmation message (`ConnectorEvidenceMessageCreator`) and submit it to the gateway via `ConnectorLinkSubmitter`.
. When `connector.message-processing.send-generated-evidences-to-backend` is enabled, also send the confirmation message to the backend.

A failure in these steps is only logged (`Failed to process evidence trigger`); the backend already received `201` (REST) or `result=true` (SOAP) when the trigger was queued.

== Evidences generated during outbound business processing

When an outbound business message is processed by `ConnectorOutboundMessagePipeline` (listener `ConnectorJmsOutboundMessagePipelineListener` on `connector.queues.outbound-message-processing-queue`), the steps run in this order:

. `ConnectorOutboundMessageValidationStep` checks the parties of the message;
. `ConnectorOutboundMessageSecurityStep` builds the ASiC-S container and the trust-ok token;
. `ConnectorOutboundMessageGatewayNameStep` sets the gateway (`default_gateway`) when none is set;
. `ConnectorOutboundMessageEbmsIdStep` generates the ebMS identifier when the backend did not set one;
. `ConnectorOutboundMessageAcceptanceStep` creates the `SUBMISSION_ACCEPTANCE` evidence;
. the message is submitted to the gateway via `ConnectorLinkSubmitter`;
. `ConnectorOutboundMessageConfirmationStep` creates the confirmation message carrying `SUBMISSION_ACCEPTANCE`, which is submitted back to the backend via `ConnectorLinkSubmitter`.

If one of these steps throws an exception, `ConnectorOutboundMessageRejectionStep` creates a `SUBMISSION_REJECTION` evidence and submits it, and the pipeline then throws `ConnectorGatewaySubmissionException`.

== Message submitted to the gateway

Messages destined for the gateway (business messages and evidence confirmation messages) are published by `ConnectorJmsGatewayLinkPublisher` to the gateway submission queue (`connector.queues.gateway-submission-queue`, `domibus.backend.jms.inQueue` in the template), where the JMS plugin of the gateway picks them up.
