= Overview

The **Connector** sits between national backend applications and the e-CODEX gateway (Domibus).
It receives business messages from backends, packages and signs them (ASiC-S container, trust-ok token, REM evidences) and submits them to the gateway; in the other direction it validates messages received from the gateway and delivers them to the right backend.

== Modules

[cols="1,3", options="header"]
|===
| Module | Content

| `connector-domain`
| Domain model: messages, evidences, processing modes, business domains, routing expressions. No Spring dependency.

| `connector-application`
| Use cases (ports and services) of the hexagonal architecture: inbound and outbound message pipelines, evidence processing, routing, user management.

| `connector-infrastructure`
| Adapters: REST and SOAP controllers, JMS listeners and publishers, JPA persistence, S3 storage, DSS-based signature and container handling, configuration properties.

| `connector-soap-api`
| WSDL and XSD of the SOAP backend API (`DomibusConnectorBackendWebService`, `DomibusConnectorBackendDeliveryWebService`) and the WS-Security policy `backend.policy.xml`. The operations are those of the backend API of the 4.x/6.x connector series; the target namespaces are `+http://connector.ecodex.eu/ws/backend/...+`.

| `connector-bootstrapper`
| Spring Boot entry point; produces `connector-ng.jar`.

| `connector-distribution`
| Packaging of the distribution ZIP (application, start scripts, sample configuration and keystores, database scripts and documentation; the JDBC drivers are packaged in `connector-ng.jar`).

| `connector-integrationtest`
| End-to-end tests (Testcontainers).

| `connector-documentation`
| This documentation (AsciiDoc, built with `./gradlew :connector-documentation:build`).
|===

== Message processing

Messages are processed asynchronously through JMS queues (see the connector queue configuration chapter of the configuration guide):

* *Outbound business message* (backend → gateway): REST or SOAP submission (P-Mode check) → outbound staging queue → outbound processing queue (party check, ASiC-S container and trust-ok token, evidence `SUBMISSION_ACCEPTANCE`) → gateway submission queue; the `SUBMISSION_ACCEPTANCE` evidence goes back through the backend delivery queue.
* *Inbound business message* (gateway → backend): gateway reception queue (P-Mode check) → inbound staging queue → inbound processing queue (routing, evidence `RELAY_REMMD_ACCEPTANCE` to the gateway, container validation) → backend delivery queue → push to the backend, or transport step `READY_FOR_PULL` for a `pull` or `passive` backend.
* *Evidence from the gateway*: gateway reception queue → inbound evidence trigger queue (status update of the referenced message) → backend delivery queue.
* *Evidence trigger from the backend*: REST or SOAP → outbound evidence trigger queue (evidence creation) → gateway submission queue, and optionally the backend delivery queue.
* *Resolved message*: when a message is confirmed or rejected, the resolved-message clean-up queue triggers the deletion of its files.
