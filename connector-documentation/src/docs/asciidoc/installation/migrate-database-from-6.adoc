[[migrate-database-from-6]]
= Migrate the Database From 6.x

Connector 7.x uses a new database schema, stores files in an S3 bucket instead of the database or the filesystem, and has no
upgrade path from the 6.x schema. Do not start 7.1.0 on a 6.x database.

The data of a 6.x installation is copied into a new 7.1.0 database and bucket with the migration tool *connector-db-migration*
(separate repository; TODO: link the final repository of the migration tool once it is moved to its organisation). The tool:

* reads the 6.x database (schema `V6.0.2`, connector 6.0.x and 6.1.x) on PostgreSQL, MySQL, MariaDB, Oracle or H2, and never writes to it,
* writes a new 7.1.0 database (empty, or initialised by a first start of 7.1.0 without messages) on PostgreSQL, MySQL, MariaDB or Oracle 23. Source and target engines can differ, for example MariaDB to PostgreSQL,
* uploads the message contents to the S3 bucket configured in `+connector.file.storage.s3.*+`, the only file storage of 7.1.0,
* writes a report, the new passwords of the migrated users and a draft 7.1.0 `application.properties` converted from the 6.x
  `connector.properties`.

It is available as an executable JAR (Java 21) and as a Docker image.

NOTE: The configuration file is converted with the rules of the chapter "Migrate Configuration From 6.x to 7.x" of the configuration guide. The draft still has to be reviewed: every value
without a certain 6.x equivalent keeps its template value and is marked `# REVIEW`.

== What is migrated

[cols="2,3", options="header"]
|===
| 6.x | 7.1.0

| Message lanes
| Business domains. The 6.x default lanes (`defaultBusinessDomain`, `defaultMessageLane`) become `default_business_domain`.

| Active P-Mode set of each lane, with its truststore
| The processing mode of the domain. Parties, services and actions are derived from the P-Mode file exactly as 7.1.0 derives them when the
file is uploaded. JCEKS truststores are rewritten as JKS.

| Messages, message info, evidences, errors
| Messages with their status, AS4 properties, evidences and errors.

| Message contents: database (`jpa`) and filesystem storage, encrypted or not
| Attachment rows and S3 objects: business XML, business document, detached signature, ASiC-S, tokens, attachments.

| Transport steps and their states
| One transport step per message, with the state history of all 6.x attempts.

| Users
| REST API users with new passwords (6.x password hashes cannot be used by 7.x), roles `ROLE_ADMIN` and `ROLE_USER`.

| `connector.properties` and the link partners stored in the database
| Draft `application.properties`.
|===

Every rule, column by column, is described in <<migrate-6-mapping>>.

== What cannot be migrated

* *Encrypted filesystem contents whose key is lost*. With `connector.persistence.filesystem.encryption-active=true` (the 6.x
  default) 6.x encrypted each file with its own AES key. The key travelled with the JSON of the message (queues, transport steps) and is not
  stored in the database. The tool finds the keys in the transport
  steps, the Artemis data directory of 6.x, the database or a key file, and migrates the files decrypted. Only files of messages that
  never reached a transport step and are no longer in the Artemis journal cannot be decrypted. Their attachment rows are migrated and
  marked deleted, and the report lists them (`PAYLOAD_UNRECOVERABLE`). Run `extract-keys` before you clean up the 6.x installation;
  it writes all keys into a file that `migrate --legacy-fs-key-file` reads.
* *Passwords* of 6.x users. Each user gets a random password (or is disabled, `--users=disable`) and must change it at the first login.
* *Messages still in the embedded Artemis queues of 6.x*. The tool reads the Artemis journal and reports how many are left
  (`LEGACY_QUEUES_NOT_EMPTY`). Let 6.x empty its queues before you stop it (see <<migrate-6-cutover>>).
* *Messages the gateway handed to the Domibus connector plugin that 6.x never fetched*. They are not in the 6.x database, and the tool
  cannot see them. The cut-over drains the connector plugin before 6.x is stopped.
* *The 6.x processing state of unfinished messages*. 7.1.0 does not continue a 6.x step. Such messages are migrated with their status
  (`CREATED`, `FAILED`, ...) and listed as `LEGACY_IN_FLIGHT`. Let 6.x finish first; `flush-status` tells when it has.
* *Evidences without XML*. 7.1.0 requires the content. They are not migrated, but their type still decides the message status.
* *Values longer than the 7.1.0 columns*, for example error stack traces (255 characters in 7.1.0). They are shortened, and the complete
  value is written to `truncated-values.jsonl` in the report.
* *Elements of former P-Modes*: 7.1.0 keeps one processing mode per domain. Historical messages that reference services, actions or
  parties of an older P-Mode point to the disabled domain `legacy_6x_archive`. The live domain accepts only what its current P-Mode
  declares.
* *A P-Mode that 7.1.0 rejects* (for example processes with different roles, or a service without `type`) is not migrated. Upload a corrected
  P-Mode after the migration.
* *The 6.x P-Mode of a domain for which 7.1.0 already has one* (7.1.0 was started with a P-Mode before the migration). The P-Mode of 7.1.0
  is kept, and the migrated messages resolve against it (`PMODE_NOT_MIGRATED_TARGET_HAS_ONE`).
* *A 6.x user whose name already exists in 7.1.0* (usually `admin`, created by the first start of 7.1.0). The 7.1.0 user and its password are
  kept (`USER_EXISTS_IN_TARGET`).

Some values are changed so that 7.1.0 can work with them:

* *Backend message ids and ebMS ids shared by several 6.x messages* (for example a backend that resent a message with the same id).
  7.1.0 looks messages up by these ids and expects one result. The newest message keeps the id; older ones get
  `<id>#6x-<connector message id>`. The originals are written to `changed-values.jsonl` (`DUPLICATE_BACKEND_MESSAGE_ID`,
  `DUPLICATE_EBMS_ID`).
* *Several transport attempts of one message* become one transport step with the history of all attempts.
* *Empty values of required columns* become `unknown`, because Oracle cannot store an empty string.

The complete list, with the reasons, is in <<migrate-6-limitations>>.

== Procedure

The migration copies what the 6.x database holds at one moment. Messages can also be in three other places, and none of them is migrated:

* in 6.x itself: messages it is processing, and messages in the queues of its embedded Artemis broker,
* in the gateway: in 6.x, Domibus talked to the connector through the *Domibus connector plugin* (6.x gateway link `gwwspullplugin` or
  `gwwspushplugin`). In 7.x it talks through the Domibus *default JMS plugin* and the ActiveMQ broker (see the gateway chapters of the
  configuration guide). A message the connector plugin received and 6.x never fetched is not delivered to 7.x,
* in the backends: submissions not yet sent to 6.x, and deliveries a backend in pull mode has not fetched yet.

The procedure empties these places in an order that loses nothing. Rehearse it first.

=== Rehearse on a copy

Rehearse days or weeks before the cut-over, on copies, never against production:

. Copy the production data: a backup of the 6.x database restored on a staging server (any engine), the filesystem storage directory
  (`connector.persistence.filesystem.storage-path`) if used, the Artemis data directory (`spring.artemis.embedded.data-directory`), which
  holds encryption keys and queued messages, and the 6.x `connector.properties` with its environment.
. Run `analyze` against the copy and read `migration-report.md`. Resolve every `ERROR` and decide on every `WARNING`. The usual decisions
  are about P-Modes 7.1.0 rejects, contents without key, duplicate ids, users and the time zone.
. Run `migrate` into a staging 7.1.0 database and bucket, then `verify`. Note the duration: it is the downtime of the real cut-over,
  because 6.x is stopped while the tool runs. Run the tool next to the 6.x database: every round trip to it counts (see <<migrate-6-limitations>>). With a remote S3 also measure with `--upload-threads` 32 (default 16).
. Start a staging 7.1.0 with the generated `application.properties`, after its `# REVIEW` markers are resolved. Check in the
  administration portal that messages, attachments, evidences and P-Modes are there. With a staging gateway and backend, also exchange test
  messages, including an evidence for a message that 6.x sent before the migration.
. Run `extract-keys` against production (and again just before the cut-over) if 6.x encrypted its filesystem storage. Keep the key file
  secret.
. Write down the commands, the duration and the decisions. Repeat the rehearsal when production changes significantly (new lanes, new
  P-Mode, another 6.x version).

=== Prepare

* 7.1.0 is installed and configured, but not started, or started only on the empty database (the tool accepts a database that 7.1.0
  initialised, as long as it holds no messages).
* The ActiveMQ broker of 7.x runs, and the Domibus default JMS plugin is installed on the gateway. It does not receive traffic yet: the
  message filter of Domibus still routes to the connector plugin.
* The empty 7.1.0 database (see <<database-configuration>>; the tool creates the tables) and the S3 bucket are reachable from the machine
  that runs the tool. The database must be set up for XA transactions as described there (PostgreSQL: `max_prepared_transactions`
  greater than `0`). The tool checks it (`TARGET_XA_NOT_READY`): with PostgreSQL's default, 7.1.0 starts but every message from the
  gateway fails and is moved to the broker's dead letter queue `ActiveMQ.DLQ`. After fixing the database, move those messages back
  to `domibus.backend.jms.outQueue` (ActiveMQ console: *Retry*).

=== Switch the gateway and flush 6.x

The order matters. New inbound traffic is first diverted to the JMS plugin, where it waits durably in ActiveMQ for 7.1.0. Only then is the
old path drained.

. *Stop new submissions.* Stop or pause the backends. Messages they already submitted are still processed by 6.x.
. *Divert the gateway.* In the Domibus administration console, open *Message Filter* and route all criteria to the JMS plugin instead of
  the connector plugin. From now on, messages and evidences from other parties, including evidences for messages 6.x sent, wait in the
  JMS plugin's out queue until 7.1.0 starts.
. *Drain the connector plugin.* 6.x keeps running. In pull mode (`gwwspullplugin`), 6.x fetches pending messages every `pull-interval`:
  wait until Domibus shows no message for the connector plugin that was not downloaded. In push mode (`gwwspushplugin`), check in Domibus
  that no push to the connector plugin failed or waits for a retry.
. *Let 6.x finish its own work*, then check:
+
[source,bash]
----
java -jar connector-db-migration-all.jar flush-status \
  --legacy-config /opt/connector6/config/connector.properties --list
----
+
Exit code `0`: no message waits for the gateway or a backend, no transport is pending and the 6.x queues are empty. Exit code `2`: the
open categories and message ids are listed. Repeat until `0`.
+
Backends in pull mode must fetch and acknowledge everything that is ready for them before 6.x is stopped. Messages and evidences that
still wait for a pull backend are migrated and 7.1.0 offers them to the backend, but 7.1.0 does not resume any other 6.x processing.
Only outbound messages that failed for good may remain; they are migrated in their current state.
. *Stop 6.x.* It must not run during the migration. The tool compares the database before and after the run and reports
  `SOURCE_CHANGED_DURING_MIGRATION`; `--resume` then completes the migration.
. Back up the 6.x database and the filesystem storage. This is the rollback point.

=== Migrate

. Run an analysis. It reads and maps everything and writes only the report:
+
[source,bash]
----
java -jar connector-db-migration-all.jar analyze \
  --legacy-config /opt/connector6/config/connector.properties
----
+
Read `migration-report.md` and compare it with the rehearsal.
. Run the migration:
+
[source,bash]
----
java -jar connector-db-migration-all.jar migrate \
  --legacy-config /opt/connector6/config/connector.properties \
  --source-timezone Europe/Vienna \
  --target-url jdbc:postgresql://db-host:5432/connector --target-user connector --target-password \
  --s3-endpoint http://minio:9000 --s3-region us-east-1 --s3-bucket attachments \
  --s3-access-key connector --s3-secret-key \
  --report-dir ./migration-report
----
+
A password option without value is asked for interactively. Every option can also be given as environment variable `MIGRATION_<OPTION>`,
for example `MIGRATION_TARGET_PASSWORD`. Without arguments in a terminal the tool asks for every setting step by step.
+
If the run is interrupted (network failure, restart of a database, Ctrl-C), run the same command again with `--resume`. Each batch of
messages is committed only after its files are stored, so nothing is half migrated.
. Check the result independently:
+
[source,bash]
----
java -jar connector-db-migration-all.jar verify --legacy-config ... --target-url ... --s3-bucket ... (same options as migrate)
----

=== Start 7.1.0

. Copy the reviewed `migration-report/application.properties` and the keystores into the configuration of 7.1.0, and apply the checklist
  below.
. Start 7.1.0. It consumes what waited in the JMS plugin's queues: new messages, and evidences for messages 6.x sent, which are matched to
  the migrated messages by their ebMS id. An evidence for a message that 6.x had already rejected (typically by its evidence timeout)
  does not change that message any more.
. Log in with a migrated user and the password from `migration-report/user-credentials.properties`, hand the passwords over, then delete
  that file.
. Re-enable the backends. They now use the backend links of 7.x.

=== Roll back

* *Before 7.1.0 processed anything:* stop 7.1.0, route the Domibus message filter back to the connector plugin and start 6.x again. The 6.x
  database was only read. Messages that arrived in the JMS plugin in the meantime must be moved back or sent again.
* *After 7.1.0 processed messages:* a rollback loses what 7.1.0 did, because there is no migration from 7.x back to 6.x. Prefer fixing
  forward; the functional test of the rehearsal is there to avoid this case.

The 6.x database is read through the 6.x configuration: `spring.datasource.*`, `${...}` placeholders (also from an env file given with
`--legacy-env-file`) and `SPRING_DATASOURCE_*` environment variables. A JNDI datasource cannot be read; give its JDBC URL with `--source-url`.

== Options

[cols="2,4", options="header"]
|===
| Option | Meaning

| `--source-timezone`
| Time zone of the 6.x server. 6.x stored timestamps without a time zone; a wrong value shifts every timestamp. Default: the zone of the
machine running the tool.

| `--source-schema`
| Schema (Oracle: owner) of the 6.x tables, when it is not the default schema of the database user.

| `--upload-threads`
| Parallel uploads per batch (default 16). The files in flight never take more than a quarter of the heap; the tool checks the largest file against the
heap before it starts.

| `--legacy-artemis-dir`, `--legacy-fs-key-file`
| Where to look for the keys of encrypted filesystem contents besides the transport steps. The Artemis directory defaults to
`spring.artemis.embedded.data-directory` of the 6.x configuration.

| `--legacy-fs-storage-path`, `--legacy-fs-encrypted`
| Overrides `connector.persistence.filesystem.storage-path` and `encryption-active` when the 6.x configuration is not given or is
outdated.

| `--users=reset\|disable\|skip`
| New random passwords (default), disabled users, or no users. With `skip` only the administrator of `+connector.admin.*+` exists.

| `--lane-mapping LANE=DOMAIN`, `--default-lane`
| Which 6.x lanes become which business domains.

| `--resume`
| Continue a migration that was interrupted (for example by a network failure). Already migrated messages are skipped; files are
overwritten, never duplicated.

| `--no-create-schema`
| Use only tables created beforehand with the initial script.
|===

Exit codes: `0` completed (possibly with warnings), `2` completed with errors (see the report), `1` failed, `3` cancelled, `64` usage
error. A run stopped by a signal reports `INTERRUPTED`; run it again with `--resume`.

Other commands: `flush-status` (has 6.x finished its work), `verify`, `convert-config` (only the draft configuration), `extract-keys`,
and `schema <ENGINE>` (the 7.1.0 DDL as the tool creates it).

=== Docker

[source,bash]
----
docker run --rm -it --user "$(id -u):$(id -g)" \
  -v /opt/connector6:/connector6:ro \
  -v "$PWD/migration-report:/work/report" \
  -e MIGRATION_SOURCE_TIMEZONE=Europe/Vienna \
  -e MIGRATION_TARGET_PASSWORD -e MIGRATION_S3_SECRET_KEY \
  connector-db-migration migrate --yes \
    --legacy-config /connector6/config/connector.properties --legacy-home /connector6 \
    --target-url jdbc:postgresql://db-host:5432/connector --target-user connector \
    --s3-endpoint http://minio:9000 --s3-bucket attachments --s3-access-key connector
----

Mount the 6.x installation when 6.x used the filesystem storage or an H2 database. Run the container with your user id
(`--user`), so that the report directory belongs to you: `user-credentials.properties` can only be read by its owner.

== Checklist before the first start of 7.1.0

[WARNING]
====
Connector 7.1.0 deletes every message that is neither confirmed nor rejected once it is older than
`connector.file-deletion.unresolved-messages.threshold`, together with its files (see the file deletion chapter of the configuration
guide). The template value is `7d`. A migrated database contains the 6.x history, and many of those messages were never confirmed, for
example when no DELIVERY evidence arrived. With `7d`, they are deleted at the first cleanup run.

The draft configuration sets `connector.file-deletion.unresolved-messages.threshold=36500d`. Keep a value longer than the history you need
before the first start, and lower it deliberately afterwards. The report counts the messages concerned (`UNRESOLVED_HISTORY_AT_RISK`).
====

* Resolve every `# REVIEW` marker of the draft configuration: keystores (copy them to `config/keystores`), backend links, broker, JWT
  secret, administrator. Backend links that 7.1.0 would refuse at startup (an endpoint without keystore, private key, truststore or `encrypt-alias`; a partner without `encryption-alias`, `certificate-dn` or `push-address`, which 7.1.0 requires also for pull partners, for
  example link partners created in the 6.x UI) are written commented out; complete them before the backends are switched over.
* If a migrated user is named like `connector.admin.username` (usually `admin`), 7.1.0 keeps that user and does not set
  `connector.admin.password`. Log in with the password from `user-credentials.properties`.
* Domains whose P-Mode was not migrated (`PMODE_REJECTED_BY_7X`, `PMODE_WITHOUT_TRUSTSTORE` in the report) need a P-Mode or a truststore
  uploaded through the administration API.
* Re-test the message exchange: the P-Mode verification modes changed meaning (see "Behaviour changes to check" in the configuration migration chapter of the configuration guide).

== Report

[cols="1,3", options="header"]
|===
| File | Content

| `migration-report.md`, `migration-report.json`
| Outcome, row counts of source and target, message statuses, uploaded objects and bytes, and every finding with a code. The codes are
explained in <<migrate-6-findings>>.

| `truncated-values.jsonl`
| Original value of every shortened field.

| `changed-values.jsonl`
| Original value of every changed field, for example a duplicate backend message id.

| `user-credentials.properties`
| New passwords of the migrated users (readable by the owner only).

| `application.properties`
| Draft 7.1.0 configuration.
|===

== How the tool was tested

* Every 6.x database engine version in use (PostgreSQL 13/15/17, MySQL 8.0/8.4, MariaDB 10.6/10.11/11.4, Oracle 23, H2) is migrated
  into every 7.1.0 engine (PostgreSQL 17, MySQL 8.4, MariaDB 12.3, Oracle 23): 40 combinations, each with a catalogue of
  hand-written and randomised 6.x databases. Every row is compared, and every migrated file is compared byte by byte.
* Failures that happen in practice are simulated: 6.x still running, lost database connections on both sides, Ctrl-C and SIGTERM
  followed by `--resume`, a wrong time zone, a latin1 source, schemas other than the default, payloads larger than the heap, wrong
  credentials, a locked H2 file, 10 000-message installations.
* The published 7.1.0 image is started on the migrated data of every target engine, also when 7.1.0 initialised the database
  first, and reads messages, files and evidences through its REST API.
* The cut-over of this chapter was carried out end to end with two connector 6.1.0 installations exchanging messages through two
  Domibus gateways: rehearsal, gateway switch, flush, migration, start of 7.1.0, then traffic between the migrated connectors and the
  unchanged 6.x backends.
