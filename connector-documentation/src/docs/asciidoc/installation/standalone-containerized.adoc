[[docker-install]]
= Standalone Deployment — Containerized (Docker)

NOTE: When upgrading from connector 6.x, first read the configuration migration guide.
Several property names changed, so check every property you carry over from an earlier version.

== Prerequisites

In addition to the common <<prerequisites>>, this option requires Docker Engine **24 or later** and Docker Compose **2.x or later** on the host.

To verify your installation:
[source,bash]
----
docker --version
docker compose version
----

=== Connector image

The Connector is distributed as a Docker image hosted in the e-CODEX registry (`scm.ecodex.eu`).
The images can be pulled without logging in.

[cols="1,3", options="header"]
|===
| Channel | Image

| Release
| `scm.ecodex.eu/docker/connector-ng:<version>` (for example `{project-version}` once released, or `latest`)

| Snapshot (built from the `develop` branch)
| `scm.ecodex.eu/ecodex-docker-snapshots/connector-ng:edge`
|===

Alternatively, build the image from the source repository with `docker build -t connector-ng:local .` (the build runs Gradle inside the container and needs internet access).

=== Image layout

[cols="1,3", options="header"]
|===
| Path in the container | Content

| `/app/bin/connector-ng.jar` | Application
| `/app/config/` | Configuration (`application.properties`, `log4j2.xml`, `banner.txt`, test keystores). Mount your own configuration here.
| `/app/data/` | Runtime data: the DSS trusted list cache (`data/tlcache`) and, once you configure it as described below, the JTA transaction log (`data/jtalog`). Mount a persistent volume here.
| `/app/temp/` | Temporary directory for uploads (`TEMP_DIR_LOCATION`).
| `/app/transaction-logs/` | Empty directory created by the image.
|===

IMPORTANT: Keep the JTA transaction log (the files `tmlog<N>.log` and `tmlog.lck`) in the data volume: set `spring.jta.atomikos.properties.log-base-dir=./data/jtalog` in `application.properties`, or add `SPRING_JTA_ATOMIKOS_PROPERTIES_LOG_BASE_DIR=/app/data/jtalog` to `connector.env` as shown in step 2.
Only with this setting is the log stored under `/app/data`, so a mount on `/app/data` persists it. Without it the log is kept in the container's working directory `/app`, which is lost when the container is removed or recreated.
Use one data volume per Connector instance: a second instance that uses the same log directory stops with `The specified log seems to be in use already`.

The container runs as the unprivileged user `connector` (UID/GID `1000`) and listens on port `30000`.
Mounted directories must be readable (and, for `data` and `temp`, writable) by that user.

== Steps

=== Step 1 — Pull the Connector image

.Release image
[source,bash]
----
docker pull scm.ecodex.eu/docker/connector-ng:latest
----

.Snapshot image
[source,bash]
----
docker pull scm.ecodex.eu/ecodex-docker-snapshots/connector-ng:edge
----

To verify that the image is available locally:
[source,bash]
----
docker images | grep connector-ng
----

=== Step 2 — Configure the environment

Create a file named `connector.env` in your working directory.
It provides the values of the environment variables referenced by the template `application.properties` (see the environment variables table in the platform chapter of the configuration guide).

.connector.env
[source,properties]
----
# Database
DB_USERNAME=connector
DB_PASSWORD=<your_password>
DB_URL=jdbc:mysql://<db-host>:<db-port>/connector?pinGlobalTxToPhysicalConnection=true
DB_DRIVER_CLASSNAME=com.mysql.cj.jdbc.MysqlXADataSource
DB_DIALECT=org.hibernate.dialect.MySQLDialect

# Keeps the JTA transaction log in the data volume (see "Image layout")
SPRING_JTA_ATOMIKOS_PROPERTIES_LOG_BASE_DIR=/app/data/jtalog

# JWT authentication (at least 32 random bytes, e.g. `openssl rand -base64 32`)
JWT_SECRET_KEY=<jwt_secret_key>
# Overrides connector.admin.password through relaxed binding
CONNECTOR_ADMIN_PASSWORD=<admin_password>

# File storage (S3 / MinIO / Silo)
S3_ACCESS_KEY=<access_key>
S3_SECRET_KEY=<secret_key>
S3_REGION=us-east-1
S3_BUCKET=attachments
S3_ENDPOINT=http://<s3-host>:<s3-port>

# Message broker (ActiveMQ Classic)
BROKER_URL=tcp://<activemq-host>:61616
BROKER_USER=<broker_user>
BROKER_PASSWORD=<broker_password>
----

NOTE: With MySQL, the JDBC URL must contain `?pinGlobalTxToPhysicalConnection=true` (the Connector uses an XA data source).
For the other databases, see the database chapter.

IMPORTANT: Host names in this file are resolved from *inside* the container.
`localhost` refers to the container itself, not to the Docker host. Use the service name (Docker Compose), the host name or the IP address of the target service.
To reach a service published on the Docker host, add `--add-host host.docker.internal:host-gateway` to the `docker run` command and use `host.docker.internal` as host name.
To reach other containers by name, start the Connector in the same Docker network (`--network <name>`).

IMPORTANT: Every variable used in `application.properties` must be defined in `connector.env`.
If one is missing, the text `${VARIABLE}` stays in the value and the startup fails with a message about that value (see the troubleshooting table at the end of this chapter).

==== Temporary files directory

The image provides the directory `/app/temp`, owned by the `connector` user with mode `700`, and sets
`TEMP_DIR_LOCATION` to this path. You do not need to define the variable in the `connector.env` file.

NOTE: When a volume or host folder is mounted on `/app/temp`, the owner and permissions of the mount
replace the ones set in the image, and the connector does not start if they do not match.
With a bind mount, make sure the host folder is owned by the container user (UID `1000` by default), is writable by it, and is not writable by group or others (mode `700`; `755` is also accepted).
A Docker named volume (for example `-v connector-temp:/app/temp`) is initialised from the image and needs no preparation.

The two failures look like this:

* The folder is not writable by the container user (for example owned by `root`): `Property: connector.file.storage.uploadTempDirectoryUsable`, `Reason: upload-temp-directory must be a writable directory`.
* The folder is writable by group or others (for example mode `775`): `Upload directory must not be writable by group or others: [/app/temp]`.


=== Step 3 — Prepare the configuration directory

Create a local `config/` directory with the following content:

----
config/
├── application.properties
├── log4j2.xml
├── banner.txt
├── keystores/
│   ├── connector-keystore.jks
│   ├── connector-truststore.jks
│   ├── backend-keystore.jks
│   └── backend-truststore.jks
└── pmode/
    └── <your-pmode>.xml
----

Paths such as `file:./config/keystores/connector-keystore.jks` are resolved inside the container, where `./config` is the folder mounted in step 4.

* Start from the template files of the distribution package (`standalone/config/` folder), or copy them from the image, for example `docker run --rm --entrypoint cat scm.ecodex.eu/docker/connector-ng:latest /app/config/log4j2.xml > config/log4j2.xml` (the `config/` directory must exist), or all of them with `docker create --name connector-tmp scm.ecodex.eu/docker/connector-ng:latest`, `docker cp connector-tmp:/app/config/. config/` and `docker rm connector-tmp`.
* Replace the test keystores with your own key material (see <<certificates-setup>>). File names are free; they are referenced in `application.properties`.
* Place the P-Mode file exported from your gateway in `config/pmode/`, or remove the `+connector.business-domains.defaults[0].pmode.*+` properties and upload the P-Mode after startup through the administration API.
* Set a real URL in `connector.link.backend[0].link-partners[0].properties.push-address`. The template value (`+http://localhost:port/services/domibusConnectorDeliveryWebservice+`) is not a valid URL and stops the startup with `push-address must be an absolute http(s) URL`. For a first start, for example `+http://localhost:8080/services/domibusConnectorDeliveryWebservice+` is accepted.

WARNING: If `pmode.file` points to a file that does not exist, the Connector aborts the startup.

NOTE: A `config/` directory that contains keystores and passwords must not be committed to a source repository.

Then edit `config/application.properties`. The file below is the template shipped with the distribution: its values are placeholders and test values (test partner `backend_alice`, sample passwords, `pmode-blue.xml`). Replace them by following the checklist in the chapter "Preparing application.properties" of the configuration guide.

.config/application.properties template (all values must be reviewed)
[source,properties]
----
include::{distributiondir}/src/main/resources/config/application.properties[]
----

TIP: For the meaning of every property, see the configuration guide. Pay particular attention to `spring.jpa.hibernate.ddl-auto` (see <<database-configuration>>) and to the items of the <<security-checklist,security checklist>>.

=== Step 4 — Run the containerized Connector

Run the container, mounting the configuration directory and a persistent data volume.
If you pulled the snapshot image in step 1, replace the image name with the snapshot one.
Add `--network <name>` (and, for a service on the Docker host, `--add-host host.docker.internal:host-gateway`) if the database, the broker and the object store are reached by container name or host name, as described in step 2:

[source,bash]
----
docker run -d \
  --name connector-ng \
  --restart unless-stopped \
  --env-file connector.env \
  -p 30000:30000 \
  -v "$(pwd)/config:/app/config:ro" \
  -v connector-data:/app/data \
  scm.ecodex.eu/docker/connector-ng:latest
----

To follow the log output:
[source,bash]
----
docker logs -f connector-ng
----

TIP: For a local evaluation environment (Connector, gateway, database, ActiveMQ and MinIO), use the `docker-compose.yml` file at the root of the source repository, as described in its `README.md`.

==== Alternative — Docker Compose

[source,yaml]
----
services:
  connector-ng:
    image: scm.ecodex.eu/docker/connector-ng:latest
    container_name: connector-ng
    restart: unless-stopped
    env_file: connector.env
    ports:
      - "30000:30000"
    volumes:
      - ./config:/app/config:ro
      - connector-data:/app/data

volumes:
  connector-data:
----

Start it with `docker compose up -d`.
The services that the Connector needs (database, ActiveMQ, object store) are not part of this file; add them, or attach the service to the network in which they run.
Without the `connector-data` volume, the DSS trusted list cache and (if configured as described under "Image layout") the transaction log are lost when the container is recreated.

=== Step 5 — Verify the runtime status

Once running, the following endpoints are available (replace `30000` with your `server.port` if you changed it):

[cols="2,3", options="header"]
|===
| Endpoint | URL
| Health | `http://localhost:30000/actuator/health`
| Application info | `http://localhost:30000/actuator/info`
| Swagger UI | `http://localhost:30000/swagger-ui/index.html`
| SOAP backend API (WSDL) | `http://localhost:30000/services/backend?wsdl`
|===

The health endpoint must report `"status":"UP"`.
The root URL `http://localhost:30000/` has no page and answers `401`; this is expected.
Log in to the administration API (`POST /api/v1/auth/login`) with the admin account configured in `+connector.admin.*+`.
The login response contains `"mustChangePassword": true` for the initial password. The administration portal asks for the change; the API does not block other calls while the flag is set.
Change the password yourself (`POST /api/v1/auth/change-password`) before the Connector is reachable by others.

== Troubleshooting startup errors

The messages below were observed with the image of this version.
The Connector writes them to the container log (`docker logs <name>`).

[cols="2,3", options="header"]
|===
| Symptom | Likely cause

| `docker: --env-file: open connector.env: no such file or directory`
| The `connector.env` file is not in the directory where the command is run.

| The container exits right after start, and the log shows `APPLICATION FAILED TO START` with `Binding to target ... failed` and `Reason: must not be blank` (or `must not be null`)
| A mandatory property is missing or empty, for example a variable that is defined without a value in the `connector.env` file.

| The failure names a value that still contains `${...}`, for example `Value: "${S3_BUCKET}"`, `'url' must start with "jdbc"`, `password authentication failed for user "${DB_USERNAME}"` or `Illegal character in path at index 1: ${BROKER_URL}`
| A variable used in `application.properties` is not defined in the `connector.env` file. The placeholder is not resolved and stays in the value. Check all of them, for example `S3_REGION`, `S3_ACCESS_KEY` or `DB_DRIVER_CLASSNAME`.

| `Could not resolve placeholder 'connector.queues....'`
| A queue property was removed from `application.properties`. See <<troubleshooting>>.

| `WeakKeyException: The specified key byte array is ... bits which is not secure enough` (shown as `Unable to start web server`)
| `JWT_SECRET_KEY` is shorter than 32 bytes, or is not defined (the text `${JWT_SECRET_KEY}` is then used as key).

| `Property: connector.file.storage.uploadTempDirectoryUsable` with `Reason: upload-temp-directory must be a writable directory`, or `Upload directory must not be writable by group or others`
| The mount on `/app/temp` has the wrong owner or permissions. See "Temporary files directory".

| `The specified log seems to be in use already: tmlog in /app/data/jtalog/`
| Another Connector instance uses the same data volume, or the folder mounted on `/app/data` is not writable by the user `connector` (UID `1000`).

| `Application run failed` with `S3Exception: Forbidden (Service: S3, Status Code: 403 ...)` or `SdkClientException: Unable to execute HTTP request: Connect to ... failed`
| Wrong S3 credentials, or an unreachable endpoint. The message appears after the line `Started ConnectorApplication`, and the container then exits: the S3 check runs at the end of the startup. If the bucket does not exist, the credentials need permission to create it, or create it manually.

| `Could not connect to broker URL: tcp://...` (repeated in the log)
| ActiveMQ is not reachable from the container. Do not use `localhost` as the host: inside the container it refers to the container itself. The Connector keeps running and retries.

| `XAER_INVAL: Invalid arguments (or unsupported command)` while the administrator is created
| MySQL URL without `?pinGlobalTxToPhysicalConnection=true`.
|===
