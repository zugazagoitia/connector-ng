[[migrate-6-limitations]]
== Limitations in detail

What the tool cannot do, why, and what it does instead. Everything in this list is reported in the migration report when it occurs.

=== What is not migrated

[cols=",,",options="header",]
|===
|What |Why |What happens
|*Messages still in the queues of the 6.x Artemis broker* |They are in the middle of 6.x processing, which 7.1.0 cannot continue. |`+LEGACY_QUEUES_NOT_EMPTY+` with their number. Let 6.x empty its queues first (<<migrate-6-cutover>>).
|*Messages in the 6.x dead letter queues* (`+DLQ.*+`) |6.x failed to process them and never stored them in its database. They never drain by themselves. |`+LEGACY_DEAD_LETTERS+`; `+flush-status+` counts them separately. Resend them from the 6.x administration UI after fixing the cause, or accept their loss (`+flush-status --accept-dead-letters+`).
|*Messages the gateway handed to the 6.x connector plugin that 6.x never received* |They are outside the 6.x database. |Not visible to the tool. The cut-over diverts the gateway to the JMS plugin first, then drains the connector plugin (<<migrate-6-cutover>>).
|*Encrypted filesystem payloads whose key exists nowhere* |6.x encrypted each file with its own key and kept the key only in the JSON of the message while processing it, not in `+MSG_CONT.CONTENT+`. The 6.1.0 queues carry message ids only (the Artemis journal held no key in a real installation). The keys survive in the transport steps, so files referenced there are recovered. The files 6.x stored when receiving a message from the gateway (ASiC-S container, tokens) are not referenced there: on 6.1.0 they cannot be decrypted after processing. |Attachment row migrated and marked deleted: `+PAYLOAD_UNRECOVERABLE_DELIVERED+` (WARNING) when the content was already delivered, `+PAYLOAD_UNRECOVERABLE+` (ERROR) otherwise. Run `+extract-keys+` before cleaning up 6.x.
|*Payloads whose bytes are gone* |6.x removes the files of confirmed and rejected messages by design; files can also be deleted outside 6.x. |Attachment row marked deleted: `+PAYLOAD_REMOVED_BY_6X+` (INFO) for finished messages, `+PAYLOAD_MISSING+` (ERROR) otherwise.
|*User passwords* |6.x used salted SHA-512 hashes; 7.1.0 accepts only BCrypt. A hash cannot be converted. |New random passwords (`+user-credentials.properties+`), or disabled users; users must change the password at the first login.
|*The 6.x processing state of unfinished messages* |7.1.0 has its own processing; it does not continue a 6.x step. |Migrated with their status (`+CREATED+`, `+FAILED+`, `+READY_FOR_PULL+`, ...); `+LEGACY_IN_FLIGHT+` lists them. Flush 6.x first.
|*Evidences without XML* |7.1.0 requires the content. |Not migrated; their type still decides the status (`+EVIDENCE_WITHOUT_CONTENT+`).
|*More than one P-Mode per lane* |7.1.0 allows one processing mode per domain. |The active one is migrated. Elements of older ones that messages reference are kept in the disabled `+legacy_6x_archive+` domain.
|*A P-Mode 7.1.0 rejects* |7.1.0 would not register it. |No processing mode for that domain (`+PMODE_REJECTED_BY_7X+`); upload a corrected one.
|*The 6.x P-Mode, when the target already has one* (7.1.0 was started with a P-Mode) |One per domain. |The target's P-Mode is kept and messages resolve against it (`+PMODE_NOT_MIGRATED_TARGET_HAS_ONE+`).
|*Lane properties, `+HASH_VALUE+`, grace login counters, gateway link configuration, 4.x-era columns* |No 7.1.0 equivalent. |Dropped, and reported where they have content.
|===

=== What is changed

[cols=",,",options="header",]
|===
|What |Why |How
|Values longer than the 7.1.0 columns (stack traces, original sender, payload names) |7.1.0 column sizes (255 for many). |Shortened; the full value is in `+truncated-values.jsonl+`.
|Backend message ids and ebMS ids shared by several 6.x messages |7.1.0 looks messages up by these ids expecting one result; duplicates break evidence correlation. |The newest message keeps the id; older ones get `+<id>#6x-<connector message id>+`; originals in `+changed-values.jsonl+`.
|Several transport attempts of one message |7.1.0 expects one step per message. |One step with the latest state and the full history of all attempts.
|Empty values of required columns |Oracle cannot store `+''+`. |`+unknown+` (`+NOT_NULL_PLACEHOLDER+`).
|Message status |7.1.0 stores a status; 6.x derived it from timestamps. |Derived by the rules in <<migrate-6-mapping>>.
|JCEKS / PKCS12S2 truststores |7.1.0 accepts JKS and PKCS12. |Rewritten as JKS / stored as PKCS12.
|Backend links 7.1.0 would refuse at startup (an endpoint without keystore, private key, truststore or `+encrypt-alias+`; a partner without `+encryption-alias+`, `+certificate-dn+` or `+push-address+`, which 7.1.0 requires also for pull partners; typically link partners created in the 6.x UI) |7.1.0 does not start with an incomplete backend link. |Written commented out in the draft `+application.properties+`, with a REVIEW note naming what is missing.
|A user of the same name already in the target |Created by 7.1.0 (usually `+admin+`). |Kept with its password; the 6.x user is not migrated (`+USER_EXISTS_IN_TARGET+`).
|===

=== Conditions the tool requires

* *6.x is stopped* during the migration. The tool compares the source before and after the run and reports `+SOURCE_CHANGED_DURING_MIGRATION+`; `+--resume+` then completes the migration.
* *`+--source-timezone+` is the zone of the 6.x server.* 6.x stored local times. Without the option the zone of the machine running the tool is used (`+SOURCE_TIMEZONE_DEFAULTED+`). A wrong zone shifts every timestamp; the tool compares evidence `+EventTime+` values with the stored times and reports a mismatch (`+SOURCE_TIMEZONE_SUSPECT+`). Only evidences with an `+EventTime+` can be checked. 6.x stored local times without offset, so a time in the hour repeated when daylight saving time ends (for example 02:30 on the last Sunday of October in Europe) can mean two instants. The tool reads it as 6.x itself read it back; such times can be one hour off.
* *The 7.1.0 database is empty*, or holds only what 7.1.0 creates at startup (no messages), or is the target of an interrupted run (`+--resume+`). Migrating into a 7.1.0 that already processes traffic is possible with `+--resume+`, but not recommended.
* *Oracle as target needs Oracle 23*: the 7.1.0 schema uses `+BOOLEAN+`.
* *H2 is a source only*, read with H2 2.2.224 (the version of 6.x). The H2 file must not be open in a running 6.x.
* *Memory:* payloads are held in memory while they are uploaded, at most a quarter of the heap at a time (plus one payload larger than that). The tool checks the largest recorded payload against the heap before it starts and stops with the `+-Xmx+` to use.
* *The target storage is S3*, the only file storage connector 7.1.0 reads. Other storage options of the tool are not ready for use and are refused against a 7.1.0 database.
* *One 6.x installation per run.* Merging two 6.x databases into one 7.1.0 database is not supported.
* *Messages are migrated by 6.x id order in batches.* Each batch is one transaction, committed only after its files are stored. An interruption loses at most the batch in flight, which `+--resume+` redoes.

=== Duration and network latency

The migration is a downtime: 6.x is stopped while it runs. Its duration depends less on the CPU than on the round trips to the three systems, in batches of 200 messages (`+--batch-size+`):

[cols="1,2,2",options="header"]
|===
|System |Round trips |Effect
|6.x database |about 5 queries per batch, plus about 3 per payload stored in the database (`+jpa+` storage: one short read-only transaction per payload) |With database storage this term dominates as soon as the tool is not next to the database: 3 000 payloads × 3 round trips × 2 ms = 18 s per 1 000 messages.
|7.1.0 database |about 30 per batch (one batch insert per table, id lookups, commit) |Small: about 60 ms per batch at 2 ms.
|S3 |one PUT per file, `+--upload-threads+` (default 16) in parallel |Latency is hidden by the threads; bandwidth matters for large files. With a remote S3 try `+--upload-threads 32+`.
|6.x filesystem storage |one file read per payload |Local disk or a fast network share; a slow NFS mount adds its latency per file.
|===

* Run the tool on a machine *next to the 6.x database* (same network or region), not across a WAN or VPN. Measured with all systems on one host (MinIO as S3) the tool migrates about 180–220 messages per second; at 2 ms of round trip to the 6.x database with database storage, expect a few tens per second.
* Measure in the rehearsal on the same network as the cut-over will use: the duration of the rehearsal is the downtime.
* A lost connection costs at most the batch in flight: the tool stops and `+--resume+` continues.

=== The converted configuration

`+application.properties+` is a *draft*. Its conversion is the part of the migration with the most room for error, because 6.x and 7.x differ in concepts, not only in names:

* *Renamed properties* are carried over only where the meaning is the same; every value without a certain 6.x equivalent keeps the 7.1.0 template value and is marked `+# REVIEW+`. Template values are test values (passwords, keystores, the JWT secret).
* *Dropped properties* are listed at the end of the draft with the reason (gateway link, embedded Artemis, 6.x UI settings, ...).
* *Keystores and truststores* keep their paths; the files must be copied to the 7.1.0 installation. JCEKS/PKCS12S2 stores must be converted (the data migration converts the P-Mode truststores, not these files).
* *Backend links* follow the exact 7.1.0 validation; a link 7.1.0 would refuse is written commented out with what is missing. Pull partners get a marked placeholder `+push-address+`. Certificate DNs are lower-cased (7.1.0 compares them in lower case).
* *Routing rules* of the same backend are merged into one rule (7.1.0 keeps one rule per backend), losing their 6.x priorities.
* *Properties stored in the 6.x database* (`+DOMIBUS_CONNECTOR_PROPERTY+`, set in the 6.x UI) override the file values, as in 6.x.
* *Behaviour changes* (P-Mode verification modes, automatic DELIVERY evidences, evidence timeouts, file deletion thresholds) are not visible in a property name: they are listed in the configuration migration chapter of the configuration guide.

What is checked automatically: the real 6.x configuration files of the 6.1.0 repository are converted in the unit tests of the tool, and its end-to-end tests and both black-box cut-overs started 7.1.0 with an unchanged draft. What is not checked: whether the values are right for the environment. Treat every `+# REVIEW+` marker as a decision, and test the exchange with the partners and backends in the rehearsal.

=== What the tool cannot check

* Messages waiting in the Domibus connector plugin of the gateway, and submissions a backend has not sent yet.
* That the generated `+application.properties+` matches the environment: keystores, broker, backends, certificates. It is a draft with `+REVIEW+` markers.
* That the remote parties and backends work with 7.1.0. The P-Mode verification modes changed meaning; re-test the exchange.
